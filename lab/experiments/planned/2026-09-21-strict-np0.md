# Planned: remove the prelude on the strict slot loop (`model.n_prelude: 0`)

Status: planned

Date: 2026-09-21 (frozen before any GPU step of the arm). Arc: the LXTUL-P note's
"[If the ladder fails](../../../.agents/notes/proposed/architecture/2026-09-21-lxtul-particles-what-gives-a-pass-a-job.md)"
section — Wolfe's direction, verbatim: "If these fail we should test removing the
prelude." Partner: `slot-spandec-strict` (`tul_slot_spandec_strict.yaml`).

## Question

The plain norm_match model earns K1−K6 **0.033** under the PRELUDE entry and **0.185**
under Parcae's noise entry (`prelude-entry-flattens-the-loop`, 2026-09-10), and the core's
blocks read near-inert on slot states under the prelude entry (MLP out/in 1-2 %). The
working explanation is that the prelude hands the loop a state already near the map's
fixed point, so passes 2..T have nothing to do. Does removing the prelude — the core
reading the embeddings directly, for the tokens and for the slot seed — move the strict
slot loop's K-curve off its +0.002 floor?

It is NOT the noise entry. `model.core_state_init: "noise"`
(`2026-09-10-arc-slot-mnext-noise-entry`) replaces `h_0` with a draw while the prelude is
still there feeding `e`; the slot loop read K1−K6 0.002 under it. Here the entry is still
`h_0 = e` and what changes is what `e` IS.

## Hypothesis

If the flat K-curve is the entry's fault, this is the arm that moves it, because it
removes the thing that makes the entry a fixed point rather than masking it. If the
K-curve is still flat with no prelude at all, the entry explanation is spent and the
remaining explanations are the target and the loss, not the state the loop starts from.

## Method

`morph/configs/tul_slot_spandec_strict_np0.yaml`: one factor over
`tul_slot_spandec_strict`, `model.n_prelude: 0` (and `model.n_layers: 10`, which is
documentation in this tree — nothing reads it; `MORPHTransformer` computes
`n_total = n_prelude + n_core + n_coda`). NO model code change.

**The block budget falls 14 -> 10, so this arm is NOT a matched-compute partner to
`slot-spandec-strict` and must not be scored as one.** The reading it exists for is the
K-curve and the per-pass instruments, which are within-run
(`tul-goal-is-loop-contribution-not-matched-compute`). A CE contrast, if anyone wants one,
needs a 10-block strict arm and that is a second run.

**The hinge has to be read first.** `model.slot_gain_lambda` is 100 at target 0.9 and it
was tuned on states the prelude produced. The noise-entry filing found `gain_est` 8.6 with
a ~6,000-nat penalty and ran on the free base. So `loop/gain_est`, `loop/slot_gain_pen`
and `loop/core_gain_t0` are read in the first 200 steps; if the penalty dominates the
loss, the arm to run is this config with `model.slot_gain_lambda: 0` on the command line
and the detonation tripwire (`preclip/total > 1e4` at any step ≥ 200) as the only hold.

CPU smoke already run (2026-09-21, no GPU): the tiny fan fixture at `n_prelude: 0` with
the span decoder on and the hinge at 100 @ 0.9 builds, and one training forward+backward
gives a finite loss and finite grads. Its hinge reading at random init is `gain_est`
0.8734 / max 0.8823 with `gain_reg_weighted` exactly 0.0, against 0.8756 / 0.8860 / 0.0 on
the same fixture at `n_prelude: 2`. That is a 64-wide random-init model with 2 core blocks
and depth ≤ 3 — it says the arm BUILDS, and it says nothing about what a 1024-wide trained
core reads at step 200.

5,000 steps, batch 6, the same seed, packer and rows as `slot-spandec-strict`.

## Predictions (frozen)

Baselines: `slot-spandec-strict` tokens K1−K6 ≈ +0.002 (twelve arms sit in
[−0.0002, +0.002], `slot-loop-k-curve-yardstick`); plain norm_match noise entry 0.185,
prelude entry 0.033. Seed spread 0.024 nats. Probabilities are the builder's, reviewed by the orchestrator 2026-09-21 03:45 and adopted unchanged before any GPU step.

- **P-1 (it runs).** 5,000 steps, tripwire HEALTHY, at `slot_gain_lambda: 100`. **55 %.**
  The hinge was tuned on prelude-shaped entries; this arm hands it embedding-shaped ones.
- **P-2 (the hinge is not free).** `loop/slot_gain_pen` above **1.0 nat** at some step in
  the first 500. **60 %.** If it is, the arm to score is the `slot_gain_lambda: 0` twin
  and that is stated here BEFORE the run so it is not a post-hoc rescue.
- **P-3 (THE ARM'S REASON).** Tokens K1−K6 above **+0.020** (ten times the slot-loop
  yardstick). **35 %.** For it: the prelude entry is the one lever with a measured 6x
  effect on a PLAIN model's K-curve. Against it: eight other levers moved the slot loop by
  ≤ 0.0023 and the entry has already been attacked once (the noise entry, 0.002).
- **P-4 (CE is worse).** Final val CE WORSE than `slot-spandec-strict` by more than 0.05.
  **80 %.** Four fewer blocks and no prelude; this is expected and is not the reading.
- **P-5 (the slot seed survives).** `val/slot_eff_rank` within **±3** of the strict arm's
  (6.3). **50 %.** The seed is now `E_slot + W_sent·embed(t_last)` with no prelude to mix
  it, which could raise the rank (less smoothing) or collapse it (no context at all).
- **P-6 (cost).** RATE at least **1.15x** the strict arm's. **85 %.** Four fewer blocks on
  every position.

## Binding

If **P-3 holds**: the prelude entry was the flattener on the slot loop too, and the whole
fan/sampler ladder should be re-cut over a no-prelude base before anything else is read on
it (the note's own rule: the ruler must move before a fan is read on it).

If **P-3 fails**: the entry explanation is spent for the slot loop. Say so in the LXTUL-P
note and in `prelude-entry-flattens-the-loop` (which is a PLAIN-model fact and must not be
read as a slot-loop one), and the remaining explanations are the target and the loss.

If **P-1 fails at lambda 100**: rerun at `model.slot_gain_lambda: 0` and read the same
curve. A detonation there closes the arm; a healthy run there is the arm.

- Nothing measured the claim that the prelude hands the loop a near-fixed-point state ON
  THE SLOT PATH; the 1-2 % MLP reading is from the plain model's audit.
