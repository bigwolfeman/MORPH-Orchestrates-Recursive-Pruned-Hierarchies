# DiffusionBlocks testbed: fidelity audit

Scope: does `/home/wolfe/11-DiffusionBlocks-Testing` implement DiffusionBlocks (arXiv
2506.14202) faithfully enough that its negative verdict ("DB loses to AR") is a test of the
paper's method, or only of the testbed's own variant? No files were modified. No experiments
were re-run; every number below is quoted from the testbed's existing logs/notes, or derived
directly from source I read.

## What I actually read

- Paper: full mirrored markdown (`diffusionblocks.md`, 1615 lines) plus a targeted
  `pdftotext -layout` pass on the local PDF to recover one OCR-garbled sentence in Appendix B
  (the markdown mirror truncated it mid-formula).
- Official code: fetched the real upstream files with `curl` (not the WebFetch summarizer,
  which I used only for a first pass and then verified byte-for-byte against the raw
  fetch) — `model.py` (292 lines, full) and `dblock_modules.py` from
  `github.com/SakanaAI/DiffusionBlocks` commit `ade0b08`, plus the repo's file listing and
  README via WebFetch. The vendored copy at `third_party/sakana_dblock_modules.py` diffs
  clean against the live raw file (only the added provenance docstring differs) — confirmed
  with `diff`, not assumed.
- Testbed: `dbref/db.py`, `dbref/model.py`, `dbref/loss.py`, `dbref/sample.py` in full;
  `dbref/train.py` and `configs/*.yaml` for the training-loop and protocol pieces;
  `tests/test_db_parity.py` and `tests/test_no_leak.py` in full; `README.md`, `PLAN.md`,
  `GATES.md`/`gates/l3-measure.md`, and all four files under `notes/`.

One fact reshapes the whole audit: **the authors released code for ViT/CIFAR image
classification only. There is no upstream language-model implementation of DiffusionBlocks,
anywhere.** I confirmed this against the live repo file listing, not just the testbed's
README claim. Everything AR/text-specific in "official code does" below is therefore N/A —
there is no oracle to check the testbed against for those cells, and the paper's prose
(Appendix E.4, and one recovered sentence from Appendix B) is the only spec that exists.

## Verdict

**(a) Documented and defensible** — deviations the testbed names, gives a reason for, and
which do not plausibly favor the negative outcome (some plausibly disfavor it, i.e. make the
comparison harder for AR / easier for DB, or are neutral):
- GPT-2 tokenizer instead of Llama-2 32K.
- Cosine LR decay shape (paper states warmup but not decay shape).
- Symmetric decoding (greedy + top-p for both arms, vs the paper's asymmetric greedy-DB/top-p-AR).
- The correct per-sample Eq. 6 weighting implemented and offered as an arm, with the literal
  (buggy) oracle behavior also reproducible via `loss_weighting: unweighted` — and measured to
  be the friendlier setting for DB.
- Two-pass concat realization of the conditioning mask, argued (though not proven) equivalent
  to the paper's literal single-pass 2L form.
- Tied readout with a derived logit scale, in place of the oracle's untied classifier (paper
  doesn't specify either way for LM).
- Running `db_b4` at both the token-matched budget AND the paper's own B×-steps
  compute-matched protocol.

**(b) Documented but material** — deviations that are honestly logged as open questions and
that plausibly move the verdict, in either direction, by an amount nobody has closed out:
- **Token budget.** 143.4M tokens is somewhere between 1/70 and 1/629 of the paper's OWT
  budget depending on which of the testbed's own two internally-inconsistent numbers you use
  (the "1/70" figure is unsourced and does not match the README's own "~90B" derivation). The
  testbed's own evidence argues this matters: `db_b4` closed 0.86 nats of the gap to AR going
  from 143M→573M tokens, and the "Not verified" list explicitly states "nothing rules out a
  crossover far past this scale."
- **The dropped noisy-self-attention-key term** in the default `concat` conditioning
  (explicitly named "THE ONE DEVIATION" in `model.py`), argued harmless but never isolated
  by an ablation, and the literal 2L single-pass form that would settle it was implemented but
  never run to a full arm.
- **MAUVE, the paper's actual headline metric for AR text, was never computed.** The testbed's
  CE-at-σ_max metric is a reasonable and arguably stricter proxy, but it is not the number the
  paper reports, so the comparison in this repo cannot be read as "reproduces Table 4 and
  disagrees" — it's a different, self-consistent measurement that never touches the paper's
  own reported numbers directly.

**(c) Undocumented** — I found exactly one, and it's a paperwork/arithmetic issue, not a code
issue: the "143.4M tokens is ~1/70 of the paper's language budget" claim in
`notes/2026-08-21-verdict-and-teardown.md` and `gates/l3-measure.md` has no derivation
anywhere in the repo and does not match the README's own "~90B" OWT estimate (which implies
~1/629, not ~1/70). I could not find the source of the "1/70" figure; it may be a leftover
from an LM1B-budget calculation that was never updated when the testbed settled on OWT-only
training. This does not affect any measured number — it's a scale estimate in prose, not an
input to any run — but it should be corrected or sourced, because right now the testbed
understates its own token-budget shortfall by roughly an order of magnitude in the exact
sentence meant to flag that shortfall.

### Does the negative result stand as a test of the paper's method?

**Mostly yes, with one clearly-scoped exception.** Every mechanical piece I could check against
either the paper's text or the byte-exact official source — equal-mass σ partitioning, γ
overlap, σ sampling, EDM preconditioning, CE loss, the σ-to-block reversal, one-block-per-step
training, the B×-steps compute-matched protocol, the soft embedding bridge, the Euler sampler
including its extra final call — matches the paper or the oracle code exactly, several to
`atol=0` numeric equality with a test that would fail on drift. The one place I would call
"reproduces the oracle's bug" is Eq. 6 weighting, and there the testbed implements the
CORRECT version, correctly identifies that the oracle's own code is buggy (verified myself,
byte-for-byte, from the live `model.py`), and shows the correct version performs worse for
DB — so fixing that bug does not rescue DB's result, it makes it slightly harder for DB.

The one change that would most directly test whether this verdict generalizes to something
closer to the paper's actual claim is **scale**: run `db_b4` (the one arm that is genuinely
paper-protocol-faithful, including the B×-steps rule) at 10× to 100× more tokens than the
573M-token point already measured, and see whether the AR/DB gap (5.53→4.67 nats at σ_max
going from 1× to 4× tokens) continues closing, plateaus, or reverses. Everything else in the
table is either verified matching or a documented, argued, small-effect deviation; token
budget is the one axis where the testbed's own data shows the gap moving substantially with
the very knob that is furthest from the paper's actual setting, and where nothing in the repo
rules out further movement.

## What I did not verify

- I did not re-run any code or reproduce any of the testbed's numbers myself; every number in
